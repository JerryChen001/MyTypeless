# 2026-10-17 慢电脑上开会转写积压、纪要迟迟不出

## 现象

Windows 真机反馈（i7-1065G7，4 核 15W 笔记本，同时开着会议软件）：
- 会议实时转写有时卡很久不输出；
- 30 分钟的会议结束后，生成纪要超过 20 分钟还没完成，CPU 和内存被占满。

macOS（M2 Pro）上没有出现。

## 原因（实测）

那场会议（32 分钟，麦克风 + 系统声音）结束后读库：

| 路 | 转写到 |
| --- | --- |
| 麦克风 | 4.7 分钟 |
| 系统声音 | 24.6 分钟 |

- **麦克风那一路先降噪再分句（D-024）。** 降噪进程是低优先级（nice 15），CPU 被识别（FireRedASR2，正常优先级）和会议软件占满时分不到时间，整路分不出句子，实时转写就停了。会议结束时，`stop` 要等积压的录音全部降噪、分句、声纹、识别完，才开始整理纪要。
- **本机各环节的速度**（CPU 已 84% 占用时测；一句 4 秒的话）：

  | 环节 | 耗时 |
  | --- | --- |
  | 分段模型找句内换人（带 8 秒参考） | 5.6 秒 |
  | 按窗口找换人（约 5 个 1.5 秒窗口） | 约 2.1 秒 |
  | 整句声纹 | 1.0 秒 |
  | 识别 | 4～8 秒（此前测） |
  | 降噪 | 0.53 秒 / 秒录音 |

  合计远超实时，越开越落后。
- 那场会议两路的参会人数都设为 1，所以每一路的话都归给一个人（D-021 的设计，不是缺陷）。
- 三个 `mt-diarize` 进程（识别、声纹、降噪）是设计如此，没有残留进程。

## 改动

- **降噪跟不上时停用**（`segmenter.ts` 的 `denoiseLagging`，落后超过 8 秒）：这一路改用原始录音分句，并换回原始录音的 VAD 门槛（`UtteranceSegmenter.useVad`）。
  - 排队中还没降噪的部分直接读临时录音的原始音频，保证时间线顺序。
  - 停用前分出的句子识别时同样读原始录音（`denoiseStopped`），守住 D-024“降噪后的声音不拿去识别”。
- **积压时不做句内换人切分**（`overloaded`，排队超过 3 句）：只算整句声纹，让识别先跟上。
- 两种降级各提示一次：“电脑较忙：已简化降噪与说话人细分，优先保证实时转写”。
- 电脑跟得上时行为不变（macOS 实测从未积压）。

## 验证

- 单测：
  - 落后判定；
  - 中途换 VAD 门槛后时间线位置连续、照常分出句子；
  - 积压判定。
- `npm run test` 115 通过；typecheck、build、docs:check 通过。
- 真机会议（同一台慢电脑）待用户验收：实时转写不再长时间停住，结束后很快进入纪要生成。

## 遗留（需要维护者决定）

- 这台电脑上识别本身（FireRedASR2，CPU）就接近实时：两路同时不停说话时，识别仍可能慢慢落后。根本办法是给慢电脑一个更轻的识别模型。按规则，换模型要用人工标注数据实测错字率，并由维护者决定，未做。
